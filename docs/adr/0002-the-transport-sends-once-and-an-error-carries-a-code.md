# Транспорт отправляет один раз, а ошибка одна и несёт код

Неверная догадка о повторе запроса даёт двойную запись или бесконечный цикл, а вызывающему нужно знать, что делать
дальше. Здесь решено, как модуль отправляет запросы и какими ошибками отвечает. Факты измерены на YouTrack
2026.1.13757.

## Решение

- **Свой `http.Transport` ничего не отправляет дважды:** keep-alive выключен, редиректы не выполняются, протокол
  только HTTP/1.1, прокси-переменные не читаются. net/http молча повторяет запрос по HTTP/2 на `GOAWAY` и по
  сломавшемуся переиспользованному соединению — оба пути закрыты. Таймауты: соединение 10 с, TLS 10 с, заголовки ответа
  60 с.
- **Модуль не повторяет ни запись, ни чтение.** Исключение — счётчик поиска задач `POST /issuesGetter/count`: на `-1`
  он повторяется один раз и без паузы, второй `-1` даёт `total: null`.
- **Ошибка одна — `*Error`:** `Code` из закрытого словаря называет, что делать дальше, `Message` — что случилось,
  `Details` — факты парами узла, `AfterWrite` — ошибка пришла после того, как инстанс принял запись, `Err` — ошибка
  транспорта под запросом без ответа. `errors.Is` сравнивает по коду с сентинелом `Err…`. `Warning` — той же формы без
  `AfterWrite`.

  | Код | Когда |
  |---|---|
  | `bad_usage` | вызов нельзя отправить как написан, в том числе по метаданным проекта; адрес или токен |
  | `unknown_name` | имя не нашлось там, где его искали |
  | `missing_required` | запись оставляет пустыми обязательные поля проекта |
  | `not_found` | `404` |
  | `denied` | `401`, `403`; проект без единого видимого поля |
  | `rejected` | `400` |
  | `upstream_failed` | `5xx` YouTrack, статус вне таблицы, сбой соединения, таймаут; поле сменилось между чтениями |
  | `upstream_invalid` | ответ не сходится с запросом; запись вернулась не тем, что записано |
  | `write_uncertain` | запись ушла, ответа о её исходе нет |

- **Граница «запрос ушёл» — `httptrace.WroteRequest`.** До неё сбой записи — `upstream_failed`, после —
  `write_uncertain`. Оборванное тело ответа под 2xx и 5xx — тоже `write_uncertain`, под остальными статусами сервер
  запись отверг. `Send` ставит эту границу записи через `Client.API()`.
- **`5xx` на запись от YouTrack (JSON-объект со строковым `error`) — `upstream_failed`.** Иначе ответил
  промежуточный узел, и это `write_uncertain`. Ошибка под 2xx после записи несёт `AfterWrite`. `MayHaveWritten()` —
  `write_uncertain` или `AfterWrite`: у ytrack это код возврата 2.
- **Слова сервера передаются дословно** под `upstream_status`, `upstream_error` и `upstream_message`. Тело целиком
  (`upstream_body`) добавляется, если статуса нет в таблице, тело не JSON-объект или несёт что-то кроме строковых
  `error` и `error_description`.
- **Статусу без тела нужной формы модуль не верит.** Не-JSON под статусом, который не 5xx, — `upstream_invalid`: по
  адресу с лишним путём перед `api/` сервер отвечает `200` и HTML-страницей веб-клиента.
- **`request` в деталях — отправленный запрос, пригодный для повторной отправки.** Пароль в userinfo маскируется, в
  query раскрыты только `,` `(` `)` `$`. Внутренние id инстанса стоят только в `request` и `upstream_*`, остальные
  ключи несут слова вызывающего. Исключение — созданные комментарий, вложение и запись времени: у них внутренний id —
  единственное имя, и `mismatch` после записи называет их им.
- **Адрес и токен проверяются в `NewClient`:** абсолютный `http`- или `https`-URL с хостом, без query и фрагмента;
  токен непустой и без управляющих символов, кроме TAB. Токен в сообщение не попадает.

## Отвергнуто

- **Тип ошибки на каждый класс исхода** (`v0.2.0`). Десять типов раскладывались на словарь ytrack таблицей в ytrack, а
  детали документа ошибки строились дважды.
- **Код из `error` сервера.** Там три словаря и ложные классы.
- **Ограничитель частоты и повтор на 5xx.** Запросы идут по одному, а повтор — решение вызывающего.
- **Чтение обратно при неизвестном исходе записи.** Создание так не проверить, и решать должен тот, кто писал.
