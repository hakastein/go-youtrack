# Запрос уходит один раз, ошибка одна и несёт код

Неверная догадка о повторе даёт двойную запись или бесконечный цикл, а вызывающему нужно по ошибке решить, что делать
дальше. Поэтому модуль ничего не повторяет сам, а каждая ошибка несёт код следующего шага. Факты — YouTrack 2026.1.13757.

- Транспорт — HTTP/1.1 без keep-alive: иначе net/http сам повторяет запрос на GOAWAY HTTP/2 и на сломанном
  переиспользованном соединении. Редиректы не выполняются, прокси из окружения не читается. Таймауты: соединение и TLS
  10 с, заголовки ответа 60 с.
- Модуль не повторяет запросы. Исключение — счётчик поиска задач `POST /issuesGetter/count`: пока не досчитал, он
  отвечает `-1`; тогда один повтор, а второй `-1` даёт `total: null`.
- Ошибка — `*Error{Code, Message, Details, AfterWrite, Err}`; `errors.Is` сравнивает код с сентинелом `Err…`.
  `Warning` — та же форма без `AfterWrite`.

  | Код | Когда |
  |---|---|
  | `bad_usage` | вызов нельзя отправить как написан, в том числе по метаданным проекта |
  | `unknown_name` | имени нет там, где его искали |
  | `missing_required` | запись оставляет пустыми обязательные поля проекта |
  | `not_found` | `404` |
  | `denied` | `401`, `403` или проект без единого видимого поля |
  | `rejected` | `400` |
  | `upstream_failed` | `5xx` YouTrack, статус вне таблицы, сбой сети, поле сменилось между чтениями |
  | `upstream_invalid` | ответ не сходится с запросом или с записанным |
  | `write_uncertain` | запись ушла, а исход неизвестен |

- Сбой записи до того, как байты ушли (`httptrace.WroteRequest`), — `upstream_failed`, после — `write_uncertain`. Обрыв
  тела ответа под 2xx или 5xx — тоже `write_uncertain`. Для записи через `API()` эту границу ставит `Send`.
- `5xx` на запись с JSON-объектом со строковым `error` — отказ YouTrack, `upstream_failed`. Любой другой `5xx` пришёл от
  промежуточного узла — `write_uncertain`. `MayHaveWritten()` — `write_uncertain` или `AfterWrite`.
- Слова сервера передаются дословно: `upstream_status`, `upstream_error`, `upstream_message`. Тело целиком
  (`upstream_body`) — если статуса нет в таблице или тело не `{error, error_description}`.
- Ответ не JSON при статусе не 5xx — `upstream_invalid`: на адрес с лишним путём перед `api/` сервер отвечает `200` и
  HTML-страницей.
- Деталь `request` — запрос в виде, пригодном для повторной отправки: в query раскрыты только
  `,()$`. Внутренние id сущностей стоят только в `request` и `upstream_*`. Исключение — созданные комментарий, вложение,
  запись времени и группы доступа тега: другого имени у них нет.
- Адрес инстанса (`ParseAddress`) — `http(s)`-URL с хостом и, если нужно, путём, и ничего больше: пользователь и пароль,
  `?` и `#`, даже пустые, — отказ. Пользователь и пароль в адресе ничего не дают: `net/http` превращает их в Basic только
  без своего `Authorization`, а клиент всегда шлёт `Bearer`. Отказ один на все случаи и адрес не повторяет.
- Токен (`CheckToken`) — непустой и без управляющих символов, кроме TAB. Токен в сообщение не попадает.

## Отвергнуто

- Свой тип ошибки на каждый класс исхода.
- Код из `error` сервера: у сервера три словаря и ложные классы.
- Повтор на `5xx` и чтение обратно при неизвестном исходе записи.
