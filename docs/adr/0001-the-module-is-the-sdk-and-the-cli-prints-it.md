# Модуль — SDK с сервисами на клиенте, а CLI печатает его документ

YouTrack нужен трём потребителям: CLI для агентов (ytrack), сервису подготовки релизов (kraken) и системе управления
тестированием (TMS). В `v0.2.0` модуль отдавал примитивы, а слой «вызов → документ» ytrack держал у себя, и знание о
YouTrack жило в двух местах. Здесь решено, где проходит граница теперь.

## Решение

- **В модуле — всё знание о YouTrack:** транспорт, сгенерированный клиент, таблица типов кастом-полей, выражение
  полей вызывающего, каталог схем и проверка имён по `$type`, построение документа ответа, проверка записи, кэш
  метаданных, ошибки со словарём кодов и фейковый сервер.
- **У ytrack остаётся то, что принадлежит CLI:** команды и грамматика флагов, поиск входа, байты вывода (`render.YAML`
  по аксессорам узла), печать ошибок и коды возврата, автодополнение, скрипты команд. ytrack — обёртка: команда
  разбирает флаги в вход операции и печатает её ответ.
- **Операции — методы сервисов на клиенте** (`c.Issues.Show`, `c.Fields.Bundle`), по сервису на сущность. Контекст
  первым аргументом, за ним то, что операция адресует, вход записи и опции указателем на структуру, `nil` — умолчания.
  Без замыканий, без глобального состояния, без флагов-указателей в опциях: `Fields string`, где пусто — поля по
  умолчанию, а `+x` — они и `x`; обновление — `*string` и `ClearX`.
- **Документная операция называется как подкоманда ytrack и отвечает `*Node`** — тем, что подкоманда печатает. Это
  функции команд API скриптов ytrack один в один. **Типизированная операция отвечает значением Go** там, где
  потребителю нужны типы: `Issues.Get`, `Issues.WriteFields`, `Fields.Metadata`, `Fields.Bundle`, `Users.Me`,
  `Users.Find`.
- **Узел — модель документа, а не YAML:** виды `NullNode`, `StringNode`, `NumberNode`, `BoolNode`, `TextNode`,
  `ListNode`, `MapNode`, пары с признаком ключа из данных. Все решения о данных принимаются при построении узла, печать —
  только байты. `MarshalJSON` пишет тот же порядок.
- **Грамматика CLI в модуль не входит.** Вход — структуры (`FieldWrite`, `IssueUpdate`, `TagSharing`, `Comments`), а
  строки `Name=value`, `--clear name` и `all|N` разбирает ytrack. Проза модуля не называет ни флагов, ни команд.
- **Задача читается `Get` с описанием и связями всегда,** потому что kraken нужны описание для списка изменений и
  родитель из связи `Subtask`. Выражения полей у `Get` нет: ответ под выражением вызывающего — документ `Show`.
- **Знание о полях экспортировано и примитивами** (`FieldType.Class`, `Encode`, `ReadValue`, `Named`, `Same`,
  `BundleFields`, `ValueKeys`) для потребителя, который собирает запросы сам через `Client.API()`.
- **Пакета три:** корневой, `ytapi` и `fake`. `youtrack → ytapi` только из адаптера `ytapi.go`; `fake` не импортирует
  ничего из модуля ([ADR-0005](0005-tests-are-contracts-against-the-fake.md)).

## Следствие

- Вход в ytrack разрешается раньше проверки вызова: клиент строится до метода, и `denied` о недостающем входе теперь
  раньше `bad_usage` о неверном вызове.

## Отвергнуто

- **Примитивы в модуле, документ в CLI** (`v0.2.0`). Знание о YouTrack в двух местах и два набора тестов одного
  поведения.
- **Конструкторы, отдающие замыкание `Call`.** Проверка раньше входа не стоит неидиоматичного API.
- **YAML в модуле.** Формат вывода CLI менялся бы вместе с модулем, а сервисам нужен узел или JSON.
- **Значение кастом-поля как объединение типов Go.** Двадцать типов дали бы двадцать ветвей у каждого потребителя.
- **Поиск входа в модуле.** Правила про `YTRACK_URL`, `auth.json` и области принадлежат CLI и его пользователю.
